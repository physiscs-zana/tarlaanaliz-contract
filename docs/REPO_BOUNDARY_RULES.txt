## 3. Contract Tuketim Kurallari

### Kural 3.1: Read-Only Submodule
Consumer repo'lar contract'i **git submodule** olarak ekler.
Submodule icerigini **asla yerel olarak degistirmez**.
Degisiklik gerekiyorsa contract reposunda PR acilir.

### Kural 3.2: Versiyon Sabitleme
Her consumer `CONTRACTS_VERSION.md` ile belirli bir versiyona pin'ler.
`CONTRACTS_SHA256.txt` ile icerik butunlugu dogrulanir.
CI pipeline'da `sha256sum -c CONTRACTS_SHA256.txt` calistirilir.

### Kural 3.3: Type Generation
- **Backend (Python):** Contract schema'larindan Pydantic modeller uretilir veya `SchemaRegistry` ile runtime validasyon yapilir.
- **Frontend (TypeScript):** Contract schema'larindan `json-schema-to-typescript` ile tip uretilir. Manuel tip tanimlamasi YASAK (KR-081 drift riski).

### Kural 3.4: Bagimsiz Validasyon (Defense in Depth)
Her katman kendi validasyonunu yapar:
- Contract repo: Schema validasyon (CI gate)
- Backend: `ContractValidatorService` ile runtime validasyon
- Frontend: Form validasyon (UX amacli, guvenlik icin degil)
Backend validasyonu **normative**'dir; frontend validasyonu **kolaylik** icindir.

## 5. RBAC Sinirlari (KR-063)

| Katman | Sorumluluk |
|--------|------------|
| Contract | Rol tanimlari (`role.enum.v1.json`, `user_role.enum.v1.json`) |
| Backend | Rol dogrulama, yetki kontrolu, JWT claim kontrolu |
| Frontend | Rol bazli UI gosterimi (route korumalari, menu filtreleme) |

**Kesin kural:** Frontend RBAC'i **gorsellestirme** icindir. Gercek yetki kontrolu **her zaman** backend'de yapilir. Frontend'te bir butonun gorunmemesi guvenlik DEGIL, UX kararidir.

## 7. Degisiklik Akisi (SDLC)

### Schema/Enum Degisikligi:
```
1. Contract reposunda PR ac
2. CI gate'leri gecir (validation, breaking-change detection, forbidden fields)
3. Breaking ise: MAJOR bump + migration guide yaz
4. Merge & release
5. Consumer repo'larda submodule guncelle
6. CONTRACTS_VERSION.md + CONTRACTS_SHA256.txt guncelle
7. Consumer CI'da hash dogrulamasi gecir
```

### Backend Degisikligi:
```
1. Platform reposunda PR ac
2. Contract uyumlulugu dogrula (schema registry test)
3. Yeni endpoint → contract reposunda once OpenAPI spec ekle
4. KR referansi ile is kuralini belirt
5. Test + CI gate gecir
```

### Frontend Degisikligi:
```
1. Web reposunda PR ac
2. Type'lar contract'tan generate edilmis olmali
3. API endpoint'leri OpenAPI spec ile uyumlu olmali
4. E2E test gecir
5. RBAC: sadece UI katmani, backend enforce
```
